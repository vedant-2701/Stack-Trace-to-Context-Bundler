**Date:** 2026-08-09
**Task(s):** Pre-T007 design revision (docs only — added task T006b)
**What happened:** While designing T007's `main.go` wiring, found that a separate `-v`/`-vv` parsing pass in `main.go` (the original assumption in plan.md's Architecture section, and T007/T008's original task text) has a real ordering bug: two independent `flag.Parse` calls -- one for verbosity, one inside `cli.ParseAll` for `--lang`/`--format` -- only work correctly if `-v`/`-vv` happen to come first on the command line. Considered a fix-up pre-pass (`ExtractVerbosity`, scanning `argv` to strip `-v`/`-vv` before handing the rest to `ParseAll`) but re-evaluation surfaced three concrete gaps in that approach (full detail in `plan.md`'s Alternatives considered): it would mishandle a positional arg named `-v` after a `--` terminator, it wouldn't recognize `--v`/`--vv` the way the stdlib `flag` package treats single/double-dash as equivalent for `--lang`/`--format`, and it would have to silently pick an interpretation for repeated `-v -v` that spec.md doesn't actually call for. Chosen fix instead: register `-v`/`-vv` directly on the same `FlagSet` already inside `ParseAll`/`ParseFixedLang`, changing both signatures to `(Input, int, error)`. This inherits the stdlib's correct `--` handling and dash-count equivalence for free and removes the ordering problem by construction (single parse, not two). Full rationale for both the chosen approach and the rejected pre-pass is recorded in `plan.md`'s Architecture / approach and Alternatives considered sections, not duplicated here.
**Deviations from plan (if any):** This *is* the deviation -- plan.md's Architecture, API/contracts, and Testing strategy sections were updated in place to reflect it (not a separate historical note, since the signature change applies going forward, not just to what's already shipped). Added task **T006b** to `tasks.md` (implements the signature change + flag registration + tests, `internal/cli` only, no `cmd/*/main.go` changes) and updated T007/T008's `Depends on` lists and task text to reference the new 3-value return and `cli.LogLevel(verbosity)` wiring.
**New open questions:** none -- both open forks (verbosity value on error paths; whether T006b should also touch main.go) were resolved before editing: always `0` on error (flat, unambiguous, and the only case that could reliably differ -- a `flag.Parse` failure -- can't reliably report a real value anyway since `-v`/`-vv` may not have been reached depending on argument order); T006b stays `internal/cli`-only since `cmd/*/main.go` don't exist as files yet and creating them early would blur into T007/T008's scope. This is a docs-only commit; T006b's implementation is a separate task/commit to follow.

**Date:** 2026-08-09
**Task(s):** Pre-T007 critical re-evaluation (docs only — added task T006c)
**What happened:** Before writing T007's `main.go`, traced through the actual runtime call sequence and found a real bug in already-shipped T004/T005/T006b code, not a style question: `ParseAll`/`ParseFixedLang` call `slog.Debug("stdin ignored...")` internally, during the same `FlagSet.Parse` call that determines verbosity. `main.go` can't configure `slog`'s handler level from that verbosity until *after* the call returns -- and Go's default (unconfigured) `slog` handler sits at `Info`, which silently and permanently discards any `Debug` call made before configuration. Net effect: the "stdin ignored" Debug log could never be observed under any `-v`/`-vv` setting, which would have failed visibly and specifically during T007's manual acceptance run-through (both-file-and-stdin-present + `-vv`, expecting to see the line, never seeing it) -- not a hypothetical, a concrete reproducible failure. Verified this by checking `log/slog`'s actual default level behavior, not just asserting it.
**Deviations from plan (if any):** Re-evaluated the fix itself (not just proposed it) before writing anything: confirmed `Input.StdinIgnored bool` + `main.go`-side logging (after configuring `slog` from the real returned verbosity) fully resolves it with no gating logic needed anywhere (`slog`'s own level filtering handles it once configured). Considered and rejected a "peek at argv for `-v`/`-vv` before calling `ParseAll`" alternative -- full reasoning in `plan.md`'s Alternatives considered, but in short: it reintroduces the exact dual-parsing fragility the T006b fix was chosen to eliminate, just scoped to logging instead of flag semantics, and has a concrete failure mode (`-- -v` as a positional arg spuriously enabling Debug output). Also decided, with Vedant's explicit sign-off on the recommendation, to drop the previously-logged `"file", fileArg` attribute from the message rather than add an `Input.FileArg` field solely to preserve it -- not spec-required, and adding a field to preserve one debug-only attribute in what spec.md itself already marks as temporary scaffolding is scope creep past KISS/YAGNI. `spec.md` needs no change: requirement 5 doesn't specify which component logs the message or its exact attributes, satisfied either way. Full rationale recorded in `plan.md`'s Architecture, Data model, Testing strategy, and Alternatives considered sections (not duplicated here); added task **T006c** to `tasks.md` and updated T007/T008's `Depends on` lists and task text.
**New open questions:** none. This is a docs-only commit; T006c's implementation is a separate task/commit to follow, same two-phase pattern as T006b.

**Date:** 2026-08-11
**Task(s):** T007 (blocked mid-verification) -- docs-only, added task T007a and ADR 0002
**What happened:** Wrote `cmd/all/main.go` and `specs/002a-cli-input-handling/verify-t007.sh` for T007's manual run-through. Vedant ran both the script and the manual commands and found `-v`/`-vv` produced zero output in every case where the flag came *after* the positional file-path argument (`stba file.txt -vv`), which is how both the script and Vedant's own manual test naturally wrote the commands. Root cause: stdlib `flag.Parse` stops recognizing flags entirely once it hits the first non-flag argument -- documented Go behavior, not a project bug, but a real usability problem for a CLI meant to be typed and piped quickly (constitution Article I). This affected **every** flag (`--lang`, `--format`, `-v`, `-vv`), not just verbosity, and had been present since T004 -- every unit test across T004/T005/T006b/T006c happened to place the file path after the flags in the constructed `args` slice, never testing the reverse order, so it went undetected until real binary usage caught it.
**Deviations from plan (if any):** This is a project-wide dependency decision, not a feature-scoped one -- per `AGENTS.md`'s Boundaries section ("never add a new third-party Go dependency without asking the user first and, if agreed, recording why in `memory/decisions/`"), this required the formal ADR process, not just a `plan.md` note like T006b/T006c used. Asked Vedant directly for the fix approach; presented three options (document the ordering constraint / adopt a real flag library / hand-roll a permutation pass), explicitly ruled out the hand-rolled option myself without asking (same category of risk already twice rejected this session: the T006b pre-pass, the T006c "peek" idea). Vedant chose adopting a library. Wrote **ADR 0002** (`memory/decisions/0002-adopt-pflag-for-flag-parsing.md`) adopting `github.com/spf13/pflag` -- full context/decision/alternatives/consequences there, not duplicated here. Key downstream consequence folded into the ADR and `plan.md`: `-v`/`-vv` move from two independently-registered bool flags to a single `pflag.CountVarP` shorthand (POSIX clustering), since `pflag` shorthands are strictly single-dash-single-character and have no direct equivalent for a literal two-character `-vv` token the way stdlib `flag` did -- `verbosityFromFlags` (T006b) becomes dead code, to be removed in T007a. Updated `plan.md` (Stack & versions, Architecture, API/contracts, Testing strategy, Alternatives considered) to match, added **T007a** to `tasks.md` (the actual code change) and marked T007 `[~]` (in progress, blocked on T007a -- `main.go` itself is written and likely doesn't need further changes, but that needs re-confirming via a fresh run-through, not assumed). `AGENTS.md` needs no text change -- its "stdlib-first" wording already accommodates a justified, recorded addition like this one, and the ADR is exactly the recording-why step that section requires.
**New open questions:** none new. T007a is next; T007's own manual run-through will be re-executed against `verify-t007.sh` once T007a lands, not assumed to pass just because the underlying bug is understood.
